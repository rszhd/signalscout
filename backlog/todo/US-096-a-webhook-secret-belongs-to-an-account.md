## Context

**`WEBHOOK_SIGNING_SECRET` is one value for the whole instance, and that is
what stops webhooks being switched on for the cloud.** US-016 wrote it as an
environment variable because there was one person on one machine. On an
instance taking registrations it is the same fault as
[BUG-010](BUG-010-a-provider-choice-is-shared-between-accounts.md): a value
keyed by the instance where it should be keyed by the account.

**The consequence is forgery, not just untidiness.** The contract is that the
customer configures the same secret at their receiver and verifies the HMAC
with it. Every customer therefore holds the value every other customer's
deliveries are signed with — so any of them can sign a payload that another's
receiver accepts as genuine, and the receiver has no way to tell.

**Nothing strips it, either.** `machine-keys.ts` takes the model keys and the
provider keys out where signup is open, on US-081's rule. It says nothing about
this secret, so a cloud worker reads it and signs with it. The rule that
protects the money does not protect the signature.

**There is also no way for a cloud customer to learn the value.**
docs/notifications.md says the secret stays in the environment and the API never
returns it, which is right for a self-hoster reading their own `.env` and
useless to somebody who does not have one. The URL field on **Monitors →
Notifications** has existed since US-016 and works; the missing half is the
secret to verify with.

**So the secret becomes a per-account row, generated by us and shown once.**
It is not a key somebody pastes — we make it, so there is nothing to test with a
provider and no probe. It follows `ai_keys`: encrypted with `ENCRYPTION_KEY`,
one row per account. Shown in full at the moment it is created and never again,
because a secret a screen will re-display is a secret that leaks with a
screenshot, and regenerating is cheap.

**The environment value stays, and stays working.** A self-hosted instance
already has receivers configured against it, and an upgrade that invalidated
every one of them would break working deliveries with nothing on screen to say
why. So the rule is the one this repository already uses for keys: an account's
row overrides the environment, and an account with no row falls back to it.

**An instance with no `ENCRYPTION_KEY` cannot hold one**, which is the same
branch the connections screen already has. It falls back to the environment
value and the screen says so, rather than offering a button that fails.

## Acceptance

- [ ] An account has its own signing secret, generated by us, stored encrypted,
      one row per account
- [ ] The delivery signs with the monitor owner's secret, falling back to the
      environment when the account has none
- [ ] It is shown in full once, when it is generated, and never again. The
      screen says so before the person leaves the page
- [ ] Regenerating is offered, and the screen says plainly that every receiver
      configured with the old value stops verifying
- [ ] A self-hosted instance with only `WEBHOOK_SIGNING_SECRET` set behaves
      exactly as it does today, with no row and no screen change forced on it
- [ ] An instance with no `ENCRYPTION_KEY` says why it cannot store one, and
      still signs with the environment value
- [ ] Two accounts, two secrets, and a test proving account A's secret does not
      verify a delivery signed for account B
- [ ] `machine-keys.ts` is revisited in the same change: either the environment
      secret is stripped where signup is open, or the ticket records why it is
      not
- [ ] A live send: a real receiver verifies a real delivery signed with an
      account's own secret

## Notes

- `ai_keys` is the shape to follow — ciphertext, a hint, one owner — and
  `credentialRecordName` is the naming rule: the ciphertext is authenticated
  with the owner in the name, so a row moved between accounts with `psql` fails
  to decrypt.
- The transport takes the secret as a constructor argument today, built once at
  worker start. Per-account signing means it is resolved per delivery, the way
  `modelsFor` resolves a model client per owner. Do not cache it for the life
  of the process without saying so.
- **A rotation must not break a delivery already queued.** A pending delivery is
  signed at each attempt, not once, so a regenerated secret changes the
  signature on a retry. That is correct — the receiver has the new value — but
  say it in docs/notifications.md.
- `pnpm db:rotate-key` walks `source_credentials` and `ai_keys`. It has to walk
  this table too. US-079 found that omission the hard way.
- Out of scope: a secret per *monitor*. A receiver is a customer's system and
  one secret per account is what they configure once.
